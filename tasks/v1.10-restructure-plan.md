# HelmLogic — v1.10 Restructure Plan

> Status doc for the v1.10 cycle restructure, kicked off post-v1.9-ship after stakeholder meetings called for a hard pivot to dealer-ops priorities. Mirrors the v1.6.2 mid-cycle restructure pattern.
>
> **Theme**: Reshuffle the entire roadmap (v1.10 onward + Backlog inflow) so dealer-ops work (Fit-up, Module management, Parts + pricing catalogs, Guided Config) ships first; customer-facing work (Send extensions, Compat Rules admin UI, SharePoint follow-ups, Lifecycle auto-transitions, etc.) pushes out but stays on the roadmap.
>
> **Trigger**: Stakeholder meetings flagged that dealer-ops is the priority. Sales-flow work (the v1.7→v1.9 customer-PDF authoring + lifecycle stack) was front-loaded; stakeholders want the dealer-facing internal-ops surfaces caught up before more customer-facing work lands.

---

## Inputs locked at planning

| Input | Decision | Why |
|---|---|---|
| Categories to move up | All 4: Fit-up · Module management · Parts + pricing catalogs · Guided Config | Stakeholders flagged every dealer-ops surface |
| Target window | v1.10 — next cycle | Hard pivot, no buffer cycle |
| Fate of customer-facing | Push out, keep on roadmap | Don't park to Backlog — keep visibility, just slide right |
| Survey source | One-shot audit script (Firestore live dump) | Authoritative — repo docs would miss anything edited in-app since last build-plan update |
| Release bucket strategy | Sequential (v1.10 → v1.20+, no half releases) | Simpler; reintroduce halves only if capacity goes amber/red consistently |
| Submitted-column triage | In-scope — anything that survives gets a status + targetRelease | Otherwise the Submitted column never drains and stories rot |

## Phase 1 — Survey (one-shot audit script)

**Goal**: Capture authoritative current state of every feature + epic in Firestore as a single JSON file.

**Deliverable**: `tasks/v1.10-restructure-survey.json`

**Steps**:
1. Add `src/lib/v110-restructure-audit.ts` — exports `auditFeaturesForRestructure(firestore)` that:
   - Queries the full `features` collection (every status, every targetRelease)
   - Queries the full `epics` collection
   - Returns a structured JSON: `{ exportedAt, epicCount, featureCount, epics: [...], features: [...] }`
   - Per feature: `{ id, title, status, targetRelease, epicId, points, dependsOn, type, priority, acceptedAt, deletedAt }`
2. Add one-shot Backlog header button: **"Audit v1.10 Restructure"** (amber, same slot as v1.1.2 / v1.3.3 / Finalise V1.9 buttons)
3. Clicking opens an AlertDialog confirming the audit will export to JSON; on confirm, runs `auditFeaturesForRestructure()` then triggers a browser download of `tasks/v1.10-restructure-survey.json`
4. User saves the file into the repo at that path; commits it

**Why a browser download not a server-side dump**: matches the existing one-shot-seed pattern (client-side Firestore SDK, no admin SDK lift). User can also re-run + diff if state drifts mid-restructure.

**Tooling reuse**: `dependsOn` field + `dependency-validation.ts` from v1.8 6.4.x — used in Phase 3 to flag retarget proposals that would violate the dep graph.

## Phase 2 — Categorise

**Goal**: Every feature in the survey JSON gets one of 5 category tags.

**Categories**:

| Tag | Definition |
|---|---|
| `dealer-ops:fit-up` | Stories under the Fit-up epic — dealer fit categories, motor dealer fit, dealer fit options merging |
| `dealer-ops:module` | Module setup, vendor module pages, model editors, variant/SKU management, pricing strategies per vendor |
| `dealer-ops:parts-pricing` | Master Price File, Sam Allen parts, pricing waterfalls, Master Data Browser, stock/inventory flows |
| `dealer-ops:guided-config` | Boat configuration + guided config flow (hull/motor matching path) |
| `customer-facing` | Send extensions, Compat Rules admin UI, SharePoint follow-ups, Lifecycle auto-transitions, anything operator-facing for customer-quote prep |
| `cross-cutting` | Decisions / tasks / content items, infra, observability, anything that doesn't slot cleanly |
| `discard` | Stale Submitted-status items, duplicates of existing stories, items that should be archived |

**Deliverable**: `tasks/v1.10-restructure-survey-categorised.md` — markdown table with one row per feature, columns: ID · title · current targetRelease · current status · proposed category. Reviewable side-by-side with the JSON.

**Steps**:
1. Walk every feature in the JSON
2. Tag by epic association + title keyword + acceptance text scan
3. Flag ambiguous cases for user clarification (don't guess silently)

## Phase 2b — Flow-on effects + gap analysis

**Goal**: Surface the downstream impact of the restructure AND identify dealer-ops stories that stakeholders expect to exist but don't.

**Why this is a real phase, not a bullet point**: Reshuffling a roadmap isn't free. Already-shipped customer-facing features (v1.7-v1.9) made assumptions about how dealer-ops behaves; if the dealer-ops layer gets reworked, those assumptions can break. And the user's stakeholders may have flagged priorities ("we need parts pricing to be reactive to vendor changes") that don't exist as authored stories yet — they live in someone's head.

**Deliverable**: `tasks/v1.10-restructure-flow-effects.md`

**Two sub-passes**:

### 2b-i. Flow-on effects across already-shipped surfaces

For every dealer-ops story being prioritised in v1.10+, walk the consumers in the v1.7-v1.9 codebase and flag risks:

| Dealer-ops change | Already-shipped surface that depends on it | Risk |
|---|---|---|
| Module-level dealer fit categories restructure | SharePoint mirror folder path (uses customer name + quote number, but pulled from quote.customer set at finalize) | Low — customer is on quote doc, not module |
| Master Price File schema rework | Quote financials calculation | Medium — `buildQuoteFinancials()` reads price levels via `getPriceForLevel()`; schema change requires resolver update |
| Compat Rules data shape change | v1.9 1.1.2 compat-rule resolver | High — the resolver expects `{kind, featureA, featureB, reason}`; field renames break it |
| Yamaha motor module changes | Motor configuration in quote flow + motor logos in PDF | Medium — `motorConfigurations[0].engines[0]` is deeply referenced |
| Trailer brand restructure | Trailer snapshot + PDF render (specifications, imageUrl, brandLogoUrl) | Medium-High — v1.4 trailer-snapshot lesson: pick-time snapshots drift silently from current data |
| User-guide content | USER_GUIDE_v1.7 / v1.8 / v1.9 docs reference specific dealer-ops UI flows | Low — docs go stale but don't crash anything; need a doc-refresh pass at end of v1.10 |

For each High-risk item: explicitly call out in the proposal which v1.10+ story includes the migration / compatibility-shim work. No High-risk surface ships in v1.10 without a migration story alongside it.

### 2b-ii. Gap analysis — missing stories

For each of the 4 dealer-ops categories, list:
- Stories that exist + are authored (from the survey JSON)
- Stories that stakeholders flagged but don't exist as authored features yet (candidate new stories)
- Implicit dependencies between dealer-ops stories themselves (e.g. "Per-vendor pricing strategy stories assume module setup story X is done; if X doesn't exist, propose it first")

**For each candidate new story**: draft a short stub with:
- Proposed title (e.g. "1.10.X — Module-level dealer fit category bulk editor")
- Type / Epic / Priority guess
- Rationale (which stakeholder signal it traces to)
- Estimated points (use Fibonacci 1/2/3/5/8)
- Proposed `targetRelease`

These become PROPOSED new stories — they don't get created until Phase 5 after user approval per-story.

## Phase 3 — Propose new layout

**Goal**: A unified proposal covering: (a) retargets of existing stories, (b) creation of approved new stories, (c) capacity budgets per release bucket.

**Deliverable**: `tasks/v1.10-restructure-proposal.md`

**Layout rules**:
1. **v1.10 fills first** with the highest-priority dealer-ops stories. Mix of all 4 sub-categories so the cycle is coherent + capacity-balanced
2. **Capacity cap per bucket**: ≤20 pts (the standing rule). Stories that don't fit slide to the next bucket
3. **Dependencies first**: if A `dependsOn` B, A can't ship in the same or earlier release than B. Run `validateRetarget()` on every proposed move
4. **Customer-facing slides right in priority order**: existing Submitted/Planned customer-facing stories keep their relative ordering, just push to later buckets. Anything currently in v1.10 slides to v1.13+ (skipping 3 buckets for dealer-ops to flow through)
5. **Submitted-status survivors** get `status: 'planned'` + a `targetRelease` assignment alongside the retarget
6. **No story moves to Backlog** unless category = `discard`
7. **High-risk flow-on items** (from Phase 2b-i) ship in the SAME release as the dealer-ops change that triggers them — or the dealer-ops change waits
8. **New stories from Phase 2b-ii** appear in the proposal alongside retargets, flagged as `[NEW]`. Each gets the same per-story row treatment

**Format per row**:

| Story ID | Title | Action | Current → Proposed | Category | Capacity impact | Rationale |
|---|---|---|---|---|---|---|
| 1.3.2 | Contract Signing Pack | retarget | v1.10 → v1.13 | customer-facing | -5 pts v1.10, +5 v1.13 | Email-blocked; flows with email-infra work |
| 1.10.X | [NEW] Module-level dealer fit category bulk editor | create | — → v1.10 | dealer-ops:fit-up | +3 pts v1.10 | Stakeholder gap; needed before per-vendor fit category sync |
| n/a | [discard] Stale duplicate of 1.4.1 | discard | submitted → archived | discard | 0 | Submitted-column triage |

**Capacity dashboard at the top of the doc**:

```
v1.10: 18 pts (90% — green) · 6 stories · fit-up x2, module x3, parts x1 · [2 NEW]
v1.11: 20 pts (100% — green) · 5 stories · ... · [1 NEW]
v1.12: 17 pts (85% — green) · 5 stories · ...
```

## Phase 4 — User approval gate

## Phase 5 — Execute (one-shot retarget + create seed)

**Goal**: Apply the approved retargets AND create the approved new stories in Firestore via a single auditable button click.

**Deliverable**: `src/lib/v110-restructure-apply.ts` + Backlog button **"Apply v1.10 Restructure"**

**Steps**:
1. Hard-code three constants from the approved proposal:
   - `RETARGET_MAP: Record<storyTitlePrefix, {targetRelease, status?}>` — for existing-story moves
   - `NEW_STORIES: FeatureDoc[]` — for newly-authored stories from Phase 2b-ii
   - `DISCARD_PREFIXES: string[]` — for Submitted-column items flagged as stale (soft-deleted via `deletedAt` + `deletedBy`, not hard-deleted, per the v1.6 lesson)
2. Button → AlertDialog confirming "This applies N retargets + creates M new stories + discards K stale items. Idempotent." → on confirm, executes:
   - **Retargets**: walk features, match by title prefix, apply `targetRelease` + `status` updates (skip if already current)
   - **Creates**: for each `NEW_STORIES` entry, check title-prefix match; if exists, skip; else `addDoc()` with the seed fields + `submitterName: 'v1.10 restructure'` + `createdAt: serverTimestamp()`
   - **Discards**: walk features, match by title prefix, set `deletedAt + deletedBy` (soft delete — recoverable via Archive view)
3. Idempotent across all three operations. Toast: `R retargets · N created · D discarded · S already current`
4. Audit-log? — NO. The Firestore subcollection rules don't include per-feature audit logs (those exist on quotes only). The proposal doc + git history capture the changes.

**Safety**:
- Same title-prefix match pattern as the existing one-shot seeds (1.1.2 Highfield compat, 1.3.3 story refresh, Finalise v1.9). Proven.
- New stories use stable `addDoc()` IDs — no client-side ID generation risk like v1.5.1's CreateFeatureDialog hotfix.
- Re-runnable. If something looks wrong post-click, we re-edit the constants, click again, the diff applies.
- Soft-delete for discards means stale Submitted-column items are recoverable from the Archive view if the wrong one got flagged.

## Out of scope for this restructure

These were considered + explicitly NOT included so the cycle stays focused:

- ❌ Story content rewrites for EXISTING stories (description / acceptanceCriteria changes) — only `targetRelease` + `status` + `epic` move. Content stays as-authored. (NEW stories from Phase 2b-ii get fresh content authored in the proposal doc; that's not a rewrite.)
- ❌ Half-release reintroduction (v1.10.5 etc.) — sequential per user's choice. Revisit only if capacity goes red consistently in Phase 3.
- ❌ Epic restructure — epics stay as-is. Stories move between releases, not between epics.
- ❌ Customer-facing v1.10 retro — what we built in v1.7-v1.9 stays as shipped. This is forward-looking only.
- ❌ Authoring new stories WITHOUT user approval — every new story proposed in Phase 2b-ii gets per-story sign-off in Phase 4. None are created until the apply seed runs in Phase 5.
