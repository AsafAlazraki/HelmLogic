## Summary

- ~95 stories audited across 17 releases (v1.7 → v2.2) + Unscheduled
- **2 CRITICAL** dependency-order violations (story directly references later-release story)
- **2 HIGH** implicit deps (depending feature can't fully function without upstream)
- **3 MEDIUM** soft deps (feature can be stub-able, cleaner if reordered)
- **4 LOW / borderline** (stale documentation, structural collisions, judgement calls)

The user-caught case (1.2.1 → 1.8.1) is the most severe and there is exactly ONE OTHER instance of the same pattern (1.2.2 → 1.8.1) hiding in the same restructure-installed cross-reference patches. Both are caused by the same root: the Quote Content Manager seed (Aug-2026) installed 1.8.x in v1.7, but the v1.7→v2.2 restructure (May-2026) pushed 1.8.1/1.8.2/1.8.3 to v1.8 and 1.8.4 to v1.9 — without retargeting 1.2.1/1.2.2 forward to match.

There is also a **structural collision** worth flagging that is not a dep-order bug per se: the restructure's NEW story `3.8.1 — Inventory / Stock display` (v1.19) collides with the catalog-manager seed's existing `3.8.1 — Inline edit: pricing fields` (v1.8.5). Both will end up in Firestore with conflicting numbering if both seeds ever run.

A separate problem: the Catalog Manager seed targets `v1.7.5` and `v1.8.5` releases that don't exist in the restructure schema. Those stories need a retarget to integer-numbered releases.

## Violations (severity-ranked)

### CRITICAL — story in earlier release directly references later-release story

#### 1. 1.2.1 Branded PDF Quote Generation (v1.7) → 1.8.1 Quote Content Block Manager (v1.8)

- **Story**: `1.2.1 — Branded PDF Quote Generation` (v1.7, 8 pts)
- **Dependency**: `1.8.1 — Quote Content Block Manager (org settings)` (v1.8, 5 pts)
- **Evidence** — cross-reference patch installed by `quote-content-manager-seed.ts` (commit 08aeae1, EXISTING_PATCHES line 138-141) into 1.2.1's acceptanceCriteria array:
  > `"Content blocks read from the Quote Content Block Manager (1.8.1) — no hardcoded copy constants"`
- **Impact**: 1.2.1 ships in v1.7 with copy hard-coded (the original seed says "all the brand intro / model story / payment plan / Why NSM blocks"). It then needs a v1.8 follow-up just to swap the source from constants → Firestore reads. That "rip out the hardcoded constants" effort isn't budgeted in 1.8.1 (which is sized at 5 pts for the *editor* surface, not the migration). The patch line is the smoking gun — it explicitly says "no hardcoded copy constants" but the only release where 1.8.1 exists is v1.8.
- **Recommended fix**: Move 1.2.1 to v1.8 (alongside 1.8.1). v1.7 capacity drops 17 → 9 pts; v1.8 grows 19 → 27 pts (over the 20-pt cap). To rebalance, push one of v1.8's smaller items (e.g. 1.3.1 Finalised Quote Locking, 1 pt) and 1.2.4 Email templates (3 pts) → v1.9. v1.9 grows 20 → 24 pts; push 2.1.1 Structured Price Sources (2 pts) → v1.10 to rebalance. End state: v1.7 = 9, v1.8 = 23 (amber, accepted), v1.9 = 22 (amber, accepted), v1.10 = 20.

#### 2. 1.2.2 Brand-Aware Content Injection (v1.7) → 1.8.1 Quote Content Block Manager (v1.8)

- **Story**: `1.2.2 — Brand-Aware Content Injection` (v1.7, 3 pts)
- **Dependency**: `1.8.1 — Quote Content Block Manager (org settings)` (v1.8, 5 pts)
- **Evidence** — second cross-reference patch installed by `quote-content-manager-seed.ts` (line 144-146) into 1.2.2's acceptanceCriteria array:
  > `"Per-brand overrides defined in the Quote Content Block Manager (1.8.1) drive the brand-specific content"`
- **Impact**: same shape as #1. 1.2.2 ships in v1.7 expecting the per-brand override surface from 1.8.1 (`organisations/{orgId}/contentBlocks/{blockId}/brandOverrides/{brandId}`) which doesn't exist until v1.8. So 1.2.2 either ships with hardcoded per-brand content (then needs a v1.8 follow-up) or is silently blocked.
- **Recommended fix**: Move 1.2.2 to v1.8 alongside 1.2.1 + 1.8.1. Add 3 pts to v1.8 — combined with the 1.2.1 move from #1, v1.8 becomes 30 pts which is over cap. Apply the same v1.9/v1.10 cascade described in #1 (push more out).

> Both critical violations have the same root cause and the same fix: **co-locate 1.2.1, 1.2.2, and 1.8.1 in v1.8** (or push 1.8.1 forward to v1.7 if 1.7 capacity allows — but at 17 pts already, adding 5 puts v1.7 at 22 pts which is over cap). **Recommendation: move 1.2.1 + 1.2.2 to v1.8.** This is the cleanest rewrite.

### MEDIUM — feature stub-able if needed but cleaner if reordered

#### 5. 8.1.4 Cross-module Quotes (v1.17) → 5.2.1 Brand & Dealer Isolation (v1.20)

- **Story**: `8.1.4 — Cross-module Quotes view with sort + filter` (v1.17, 5 pts)
- **Dependency** (implicit): `5.2.1 — Brand & Dealer Isolation (RBAC + leakage tests)` (v1.20, 8 pts)
- **Evidence** — 8.1.4 acceptanceCriteria (line 119 of sales-ops seed):
  > `"Quotes capped to org scope (no cross-org leakage per Epic 5)"`
- **Impact**: 8.1.4 explicitly cites Epic 5 isolation but Epic 5's hard-isolation story (5.2.1) ships 3 releases later. In practice today's app already does basic org scoping at the Firestore-rules level (existing v1.0–v1.6 functionality), so the cross-module Quotes view CAN ship with that as the safety net. But if a sub-dealer scenario surfaces in the v1.17 cross-module view that the existing rules don't cover, there's no leakage-test infrastructure to detect it. Borderline because the feature works; the safety net is weaker than v1.20.
- **Recommended fix**: Either (a) accept the risk and document that v1.17 cross-module views rely on existing org-level Firestore rules (no new isolation guarantees until v1.20), or (b) move 5.2.1 forward to v1.17/v1.18. (b) is cleaner. Pulling 5.2.1 to v1.18 grows v1.18 from 19 → 27 pts (over cap, would need to push two stories out). (a) is the pragmatic choice — log the dep in v1.17 release notes.

## Process recommendations

How to prevent this class of bug in future. 4 concrete suggestions ranked by leverage:

### 1. Add a `dependsOn: string[]` field to the feature schema (HIGH leverage)
Every feature gets an explicit array of story ids (or title prefixes) it depends on. Firestore rule + UI validation: when retargeting a feature, refuse the write if any `dependsOn` entry has a `targetRelease > newTargetRelease`. The Roadmap and Backlog UIs render a red "blocked by 1.8.1" badge on any card with an unsatisfied dep in its current column. This catches every CRITICAL violation at edit-time — no audit pass needed.

### 2. Pre-merge regex check on acceptanceCriteria text (LOW leverage, easy)
Add a unit test to the planning seed test suite that scans every acceptanceCriteria string for the pattern `/(\b\d+\.\d+\.\d+\b)/g` and asserts every matched story id resolves to a feature in the seed AND has `targetRelease ≤ this story's targetRelease`. Catches both the 1.2.1 / 1.7.4 cases. Runs in CI on every seed change.

### 3. Standardise cross-ref language (LOW leverage, hygiene)
Adopt one phrase, `DEPENDS ON x.y.z`, anywhere a story has a hard cross-story dep. No more "via", "reads from", "references", "Cross-reference to", "Companion to" — all of which obscure the dep graph. Combined with #2, the regex becomes deterministic.

### 4. Roadmap visual indicator for unsatisfied deps (MEDIUM leverage, UX)
On the Roadmap screen, any feature card whose `dependsOn` includes a story in a later column gets a red border + "BLOCKED" badge. A user dragging a card to an earlier release than its dep blocks it on drop with a toast. This catches the human-error case where someone retargets a story without checking deps. Couples cleanly with #1.
