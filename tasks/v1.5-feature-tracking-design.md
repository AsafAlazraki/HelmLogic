# v1.5 Feature Tracking — Design

> Status: Design shipped on `claude/app-overview-wKiZ1`.
> Companion: `v1.5-feature-tracking-status.md` (live state).
> Inspired by: `OrenAlazraki/act-ai-platform` (public) — borrowed the
> `acceptanceCriteria: string[]` pattern from its Task model.

---

## 1. Goal

Give the whole team a single, frictionless place to:

1. Submit a feature request / bug / improvement.
2. Describe it well (rich text + images + acceptance criteria).
3. Vote, comment, and reprioritise collaboratively.
4. Track it through a Kanban flow from "just submitted" to "shipped".

Every signed-in user can do every action — no roles, no approval gates.
Spec explicitly calls this out: "think very agile".

---

## 2. Data model

### `features/{featureId}`

```
features/{featureId}:
  title:              string                     (≥3 chars)
  description:        string (HTML from TipTap)
  type:               'feature' | 'bug' | 'improvement'
  status:             'submitted' | 'under-review' | 'planned' | 'in-progress' | 'shipped'
  priority:           'critical' | 'high' | 'medium' | 'low' | 'nice-to-have'
  targetRelease:      string | null              (free text, e.g. "v1.5", "v1.6", "Unscheduled")
  tags:               string[]                   (lowercased)
  voteIds:            string[]                   (user uids — one vote per user)
  order:              number                     (fractional index within column)
  acceptanceCriteria: string[]                   (Agile-style bullets)
  imageUrls:          string[]                   (max 10; features/{id}/... in Storage)
  commentCount:       number                     (denorm for card badge)
  submitterId:        string
  submitterName:      string                     (resolved at create time from profile)
  createdAt:          Timestamp (serverTimestamp)
  updatedAt:          Timestamp (serverTimestamp)
```

### `features/{featureId}/comments/{commentId}`

```
body:        string
authorId:    string
authorName:  string                              (resolved from profile at post time)
createdAt:   Timestamp (serverTimestamp)
```

---

## 3. Security rules

Fully open to any signed-in user (per spec):

```
match /features/{featureId} {
  allow read, write: if isSignedIn();
  match /comments/{commentId} {
    allow read, write: if isSignedIn();
  }
}
```

Deliberately no ownership check — anyone can edit, move, delete, or
re-tag anyone's feature. The board is a shared whiteboard.

## 5. Columns

```
Submitted     → slate  (default entry point)
Under Review  → amber
Planned       → blue
In Progress   → violet
Shipped       → emerald
```

Each column has its own sort mode (per-column, board-level state):

| Mode | Sort | Drag |
| --- | --- | --- |
| `manual`  (default) | `order` ASC | enabled |
| `votes`             | `voteIds.length` DESC | **disabled** |
| `date`              | `createdAt` DESC | **disabled** |

Drag is disabled in non-manual modes because otherwise a drop would
write `order`, then the active sort would override position on next
render → card visually snaps back.

---

## 6. Drag-and-drop

- `@dnd-kit/core` + `@dnd-kit/sortable`
- Single `DndContext` wraps all 5 columns — cards can move between.
- `PointerSensor` with `activationConstraint: { distance: 5 }` — a
  plain click doesn't start a drag, so the card stays clickable to
  open the detail sheet.
- Each column body is `useDroppable({ id: column.key })` so empty
  columns accept drops (drop on empty column = append to end).
- **Fractional-index reordering**: on drop, `newOrder` is the midpoint
  between the two neighbour cards' `order` values (or ±10 if edge).
  No bulk renumber, which means two users can reorder simultaneously
  without fighting.
- **Optimistic UI**: dropped card shows in its new position
  immediately via a local override map, which is cleared once the
  Firestore snapshot catches up, or rolled back if the write fails.

## 7. Rich text editing

TipTap + StarterKit with a minimal toolbar:

- Heading 2, Heading 3
- Bold, Italic
- Bullet list, Numbered list
- Link (with edit/remove)
- Undo, Redo

Stored as HTML. Read-only rendering uses `FeatureDescriptionView`
(same prose classes as the editor so the output matches the input).

---

## 8. Image uploads

- `FeatureImageUploader` writes to `features/{featureId}/...` in
  Firebase Storage and stores the resulting download URLs in
  `imageUrls[]`.
- Both file upload and paste-URL modes.
- **Client-side feature ID generation** in the create dialog so
  uploads work before the feature doc is saved:
  ```ts
  const [featureId] = useState(() => doc(collection(firestore, 'features')).id);
  ```
- Max 10 images (configurable).
- Grid preview with hover-to-remove.

---

## 9. Vote and comment

- Vote: `arrayUnion(uid)` / `arrayRemove(uid)` on `voteIds`. Vote count
  = `voteIds.length`. Clicking the vote button stops propagation so it
  doesn't open the detail sheet or start a drag.
- Comment: addDoc to subcollection + `increment(1)` on
  `commentCount` denorm so the card badge updates without the card
  having to subscribe to the comments subcollection. Delete decrements.

## 11. Out of scope for v1.5

- Email / Slack notifications on new features or comments
- @-mention autocomplete in comments
- Search and filter bar (tag filter, text search across titles)
- "My features" view
- GitHub issue sync
- Roadmap / timeline view
- Permission model — roll back from "everyone can do everything" to
  a reviewer/submitter split if the free-for-all gets messy in practice.

These are explicitly deferred. Capture in `tasks/v1.6-*-design.md` if
demand materialises.
