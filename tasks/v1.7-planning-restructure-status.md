## Source-of-Requirements Decisions Locked In

These are the calls Mark + Asaf made during the May-2026 backlog-gap consultation. Documented here so future-me doesn't re-litigate them mid-build:

### Per-release point cap: 20
- `POINTS_AMBER`: 35 → **16** (everything 16+ shows amber on the Roadmap)
- `POINTS_RED`: 50 → **21** (anything over the cap goes red)
- Five releases (v1.7, v1.8, v1.8.5, v1.9, v1.9.5) intentionally land in amber. Stakeholders accepted those bands during planning — not a problem to solve, a known overweight.

### Forward-planning: no more `.5` fractional releases
- v1.5.1 and v1.6.1 keep their slots because they shipped that way. Forward-planning sticks to whole-numbered releases.
- v1.7.5, v1.8.5, v1.9.5 in this seed are exceptions baked in for stories that genuinely belong "between" two releases (e.g. Sales Ops 8.1.1 needs a Q2-week-3 slot).
- After v1.9.5, no more `.5` releases. The schedule runs straight v1.10 → v2.2.

### Pipeline = existing 1.4.x lifecycle states
- The Sales Workspace (Epic 8) does NOT add a new pipeline schema. It wraps tooling around the existing `quote.status` field.
- This is what kept Sales Ops scope manageable — 4 new stories instead of 4 + a schema migration.

### Fit-Up data model: one cost + one tier per item
- Per-item, not per-row-breakdown. `cost: number` + `tier: 'simple' | 'medium' | 'complex'` on each fit-up catalog item.
- Customer-facing PDF: SINGLE summary line `Fit-up & rigging: $X (ex GST) / $Y (inc GST)`. No itemised breakdown on the customer surface.
- Internal salesman view (quote detail page) keeps the itemised breakdown for margin / diagnosis. Separate render, not a per-org toggle.

### 2.1.2 vs Epic 9 — coexist, cross-reference
- 2.1.2 (per-MODEL fit-out) stays in place. Different concept from Epic 9 (per-ITEM fit-up). Cross-ref line added to 2.1.2's acceptance.

### Master Catalog Manager: full Pricing Manager parity, then decommission
- 3.7.5 parity audit gates the 3.8.7 decommission. Never silently lose a capability.

## Known Gotchas (for testers + future-me)

- **All four seeds were idempotent.** Re-running was safe at every step. Skip-by-title for new stories, skip-if-equal for retargets, skip-if-already-present for cross-references. If anything looks off, re-clicking the (now-removed) buttons would have been the diagnostic — but the buttons are gone now. Diagnose via Firestore directly.
- **`retargetsMissed[]` was zero on the restructure run.** The seed reports any retarget whose title prefix didn't match a live story. Final run: clean. If a future seed run reports misses, check whether the title was edited mid-flight and update the prefix list in the seed file (only relevant if a future seed needs to retarget — none currently planned).
- **Master Catalog stories ship `status='submitted'`, not auto-accepted.** Mark + Asaf review each one individually. The other seeds (Sales Ops, Quote Content, restructure) auto-accept their stories via the seed runner's `submitterName`.
- **Fractional release keys mid-stream.** `release-schedule.ts` includes v1.7.5, v1.8.5, v1.9.5, v1.6.1, v1.5.1 — the latter two are shipped historical, the first three are forward-planned. Don't strip `.5` keys without confirming the underlying stories were retargeted first.
- **`EpicColor` type extended; old code may need updates.** Anywhere a `Record<EpicColor, string>` lookup exists, `'cyan'` must have an entry. v1.6.2 swept the four known sites (`feature-tracking-board.tsx`, `create-epic-dialog.tsx`, `roadmap-view.tsx`, `backlog-view.tsx`). If a new component reads epic color in the future, it must include cyan.
- **The seed modules are gone.** All four `*-seed.ts` files are deleted. If a future planning rewrite needs to re-issue similar mass changes, copy the pattern from git history (`28dc503`, `08aeae1`, `8d0a846`, `0554a41`).
