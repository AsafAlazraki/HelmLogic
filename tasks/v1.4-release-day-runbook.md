## 4. ROLLBACK (if something is wrong)

**When to pull the trigger:** multiple users blocked, pricing visibly wrong on quotes, proposal PDF crashing, critical data-loss.

**When NOT to pull:** one user reports a cosmetic bug, single broken button, non-blocking UX issue. Those are v1.4.1 work, not rollbacks.

### 4a. One-command revert

```bash
git fetch origin
git checkout main
git pull origin main
git revert -m 1 <MERGE_SHA_FROM_STEP_2B> --no-edit
git push origin main
```

That's it. Firebase App Hosting rebuilds automatically.

### 4b. What's safe to leave behind

- Firestore `modules/*.associatedModuleIds[]`, `.trailerDealerFitCategories[]`, `.moduleType === 'trailers' | 'rego'` — dangling, unread by v1.3 code. Harmless.
- Firestore `models/*.trailerAssignments[]` — dangling. Harmless. (Minor risk: if someone edits a model on reverted v1.3, the field gets stripped from that one doc. Re-added on re-merge.)
- Firestore `organisations/*/trailerOverrides/*` — entire collection is orphaned but unreachable. Harmless.
- Firestore `users/*/quotes/*.trailer.catalog.pricingSource` — unread field on saved quotes. Harmless.
- Pre-v1.4 view of a 'trailers' or 'rego' module: renders as a generic placeholder (line 683 in `modules/[id]/page.tsx` pre-revert). Annoying, not broken.

### 4c. Firestore rules

Rules deployed separately. If you deployed v1.4 rules (adding the `trailerOverrides` rule), you can leave them in place after a revert — they're permissive additions, not tightening.
