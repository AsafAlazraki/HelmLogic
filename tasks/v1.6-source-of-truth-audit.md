# v1.6 — Source-of-Truth Audit

> Audit of all 106 backlog items against the principle:
> **HelmLogic is the system of record for the sales lifecycle. Other systems are downstream mirrors / sinks — HelmLogic pushes, never depends-to-pull.**
>
> Date: 2026-04-27 · Branch: `claude/app-overview-wKiZ1`

---

## Audit framework

For each story in the backlog, I asked:

1. **Where does the data live?** If HelmLogic, ✓. If elsewhere, why?
2. **Direction of integration?** Outbound (HelmLogic → other) is good. Inbound-only (other → HelmLogic) is risky — creates a dependency.
3. **One-time bootstrap vs ongoing sync?** Imports for catalog data (one-time) are fine. Live ongoing pulls from external systems would compromise SoT.
4. **What's the contingency** if the downstream system is unavailable? HelmLogic should keep working.

Domains HelmLogic owns at MVP:

| Domain | Owner | Notes |
|---|---|---|
| Customer data | **HelmLogic** ✓ | Migration in once; HelmLogic SoT thereafter |
| Quote data | **HelmLogic** ✓ | Generated in HelmLogic; PDFs mirrored to SharePoint |
| Contract data | **HelmLogic** ✓ | Same as quotes |
| Variations | **HelmLogic** ✓ | Same |
| Pricing (live) | **HelmLogic** ✓ | Vendor lists imported once, HelmLogic SoT thereafter |
| Brand / model catalog | **HelmLogic** ✓ | Same |
| Promotions | **HelmLogic** ✓ | Created in HelmLogic |
| Comms / notes | **HelmLogic** ✓ | All inbound + outbound logged |
| Activity audit log | **HelmLogic** ✓ | Source of compliance evidence |
| Document storage | **HelmLogic + Firebase Storage** ✓ | SharePoint is a copy, not the master |

Domains that are **downstream sinks** (push from HelmLogic):

- **SharePoint** — receives quote PDFs (1.3.3)
- **Accounting / ERP** — receives settlement payloads (was 2.5.2 Revolution; now generic)
- **Email (Trigger Email extension)** — receives quote-sent / variation / reminder messages
- **(Future) Marketing automation** — possibly sync customer data later

## Gaps — what I think is MISSING (7 candidate new stories)

These are stories the spec implies but doesn't explicitly call out. I'd add them under existing epics — no new epics needed.

### G1 — Outbound sync architecture (feature) → Epic 2 / v1.9.5
- Why: Right now only SharePoint write (1.3.3) and accounting export (2.4.6) are explicit. There's no shared pattern.
- What: A small outbound event/queue pattern (writes a `mail/` style "sync queue" collection; an extension or function picks up and pushes). Standardises future integrations (DocuSign, Mailchimp, etc).
- Acceptance: queue collection schema, retry semantics, audit logging.

### G2 — Inbound import idempotency (improvement) → Epic 3 / v1.9
- Why: Codified in v1.4 as a lesson but not yet a story. Critical for repeated imports.
- What: All importers (pricing, specs, photos, marketing copy) detect a natural key (Part Number / Model Code / SKU) and upsert. Existing rows update; new rows insert; rows missing the key are skipped (toast). Already partially implemented for trailers + Yamaha MPF.
- Acceptance: per-importer key detection, upsert behaviour, summary toast (`N updated · M created · K skipped`).

### G3 — Audit log retention policy (decision) → Epic 5 / v2.0
- Why: 5.5.1 Activity Log is in v2.0 but doesn't specify retention.
- What: Decision on retention period — 1 year? 7 years (legal min)? Forever? Storage / cost implications.

### G4 — Customer data export / right-to-port (feature) → Epic 5 / Unscheduled
- Why: AU Privacy Principle 12 requires individuals can request their personal data. Different from 5.5.4 (deletion).
- What: Admin action on customer detail "Export their data" → CSV/JSON of every field + linked records.
- Acceptance: complete data export, machine-readable format, audit logged.

### G5 — Master data ownership matrix (decision) → Epic 3 / v1.7.5
- Why: Different team members / roles own different slices (brand captain owns model copy; finance owns pricing; sales leadership owns templates). Worth a single source of clarity.
- What: A short doc that names the human owner for each data domain. Lives outside HelmLogic but referenced from Settings.

### G6 — Backup / disaster recovery posture (decision) → Epic 5 / Unscheduled
- Why: Firestore has scheduled backups; do we want to opt in? Cost vs RPO tradeoff.
- What: Enable Firestore daily backups + 30-day retention. Tested restore drill once.

### G7 — Stable read API for partners (feature) → Epic 5 / Unscheduled
- Why: If a sub-dealer wants to embed quote-status in their site, or if Revolution / accounting wants to poll, going through Firestore client SDK isn't right. Needs a versioned read API.
- What: Cloud Function HTTP endpoint with API-key auth, exposing read-only endpoints for `customers/{id}`, `quotes/{id}`, `contracts/{id}`. Versioned (`/v1/...`).
- Acceptance: API key generation in admin, rate limiting, OpenAPI spec.
