# 1.8.1 — Quote Content Block Manager (Design)

> Story: **1.8.1 — Quote Content Block Manager (org settings)**
> Release: **v1.7** (5 pts, critical priority)
> Foundation for: 1.2.1 Branded PDF, 1.2.2 Brand-Aware Content Injection
> Followed by: 1.8.2 Image Upload (v1.7), 1.8.3 Layout Controls (v1.8)

---

## 1. What we're building

A new **Quote Content** tab in org settings that lets admin users edit the rich-text blocks the customer-facing PDF renders. Each block has a fixed type (terms-and-conditions, why-us, brand-story, etc.) wired to a known position on the PDF. Each block can have **per-brand overrides** keyed by `vendorId`, plus a **version history** drawer for safe edits.

This story replaces the existing plain-text T&Cs textarea (single string, single org-wide value) with a TipTap-based multi-block manager. The existing `organisation.termsAndConditions` field is auto-migrated into a `terms-and-conditions` content block on first open of the new tab.

Critically: 1.8.1 is the foundation that **unblocks 1.2.1 + 1.2.2** in v1.7. Both reference 1.8.1 in their acceptance criteria. Build order in v1.7: **1.8.1 → 1.2.1 → 1.2.2 → 6.4.x**.

## 3. Data model

### Firestore — one new subcollection

```
organisations/{orgId}/
  contentBlocks/{blockId}                ← org-default content for each block type
    blockType: 'terms-and-conditions' | 'salesperson-message' | 'why-us' |
                'brand-story' | 'after-sales' | 'finance-info' | 'value-summary'
    html: string                          ← TipTap HTML (default body)
    startsOnNewPage: boolean              ← schema-only in 1.8.1; UI lands in 1.8.3
    createdAt: Timestamp
    updatedAt: Timestamp
    updatedByUid: string
    updatedByName: string

  contentBlocks/{blockId}/brandOverrides/{vendorId}    ← per-brand variant
    html: string                          ← overrides parent's html when quote.vendorId === {vendorId}
    updatedAt: Timestamp
    updatedByUid: string
    updatedByName: string

  contentBlocks/{blockId}/versions/{versionId}         ← history (default + per-brand share this)
    html: string                          ← snapshot of html at save time
    level: 'default' | `brand:{vendorId}` ← which surface saved it
    savedAt: Timestamp
    savedByUid: string
    savedByName: string
```

### Block types (fixed enum, ordered)

| Order | blockType | PDF position | Default content (from migration / seed) |
|---|---|---|---|
| 10 | `salesperson-message` | Page 1, below cover header | "" (empty until org adds one) |
| 20 | `why-us` | Page 1, below salesperson message | "" |
| 30 | `brand-story` | Page 2, top | "" |
| 40 | `after-sales` | Page 2, after vessel config | "" |
| 50 | `finance-info` | Page 3, before pricing table | "" |
| 60 | `value-summary` | Page 3, after pricing table | "" |
| 70 | `terms-and-conditions` | Page 3, above signature lines | Migrated from `organisation.termsAndConditions` (or DEFAULT_TERMS if empty) |

The `order` field on the doc is used for stable client-side sorting; the `blockType` enum drives PDF position resolution.

### Resolution logic (consumed by 1.2.1)

```ts
// src/lib/content-blocks.ts
export async function resolveContentBlocksForQuote(
  firestore: Firestore,
  orgId: string,
  vendorId: string | null,
): Promise<Record<BlockType, string>> {
  const blocksSnap = await getDocs(collection(firestore, `organisations/${orgId}/contentBlocks`));
  const result: Partial<Record<BlockType, string>> = {};

  for (const blockDoc of blocksSnap.docs) {
    const block = blockDoc.data() as ContentBlock;
    let html = block.html;

    if (vendorId) {
      const overrideRef = doc(firestore, `organisations/${orgId}/contentBlocks/${blockDoc.id}/brandOverrides/${vendorId}`);
      const overrideSnap = await getDoc(overrideRef);
      if (overrideSnap.exists()) {
        html = (overrideSnap.data() as BrandOverride).html;
      }
    }

    result[block.blockType] = html;
  }

  return result as Record<BlockType, string>;
}
```

This is the function 1.2.1 will call at PDF-generation time.

## 4. Migration — existing T&Cs → content block

Two-prong, idempotent:

### Auto-migrate on first open of the new tab

When the Quote Content tab first mounts for an org, check:
```
if (organisation.termsAndConditions && contentBlocks.length === 0) {
  migrate();
}

async function migrate() {
  const blockId = doc(collection(firestore, `organisations/${orgId}/contentBlocks`)).id;
  await setDoc(doc(firestore, `organisations/${orgId}/contentBlocks/${blockId}`), {
    blockType: 'terms-and-conditions',
    html: textToTipTapHtml(organisation.termsAndConditions),  // wrap each line in <p>
    startsOnNewPage: false,
    createdAt: serverTimestamp(),
    updatedAt: serverTimestamp(),
    updatedByUid: user.uid,
    updatedByName: 'Migrated from textarea',
  });
  toast({ title: 'T&Cs migrated to content block', description: 'You can now edit it with rich text + add per-brand overrides.' });
}
```

The `organisation.termsAndConditions` field is **left in place** (do NOT delete) so the PDF still has a fallback. See next.

### PDF render with fallback (changes in 1.2.1, not 1.8.1)

When 1.2.1 ships, the PDF render becomes:
```ts
const blocks = await resolveContentBlocksForQuote(firestore, orgId, quote.vendorId);
const tcHtml = blocks['terms-and-conditions']
  ?? textToTipTapHtml(organisation?.termsAndConditions ?? '')
  ?? textToTipTapHtml(DEFAULT_TERMS.join('\n'));
```

So an org that hasn't opened the Quote Content tab yet still gets their T&Cs on the PDF (read from the legacy field). Once they open the tab, auto-migration fires, contentBlocks become source of truth, the legacy field becomes dead but stays for safety.

A future cleanup story (post-MVP) can sweep `organisation.termsAndConditions` deletion once every org is migrated. Out of scope for v1.7.

## 6. Build phases (4 commits, sequential)

### Phase A — Schema, types, migration helper (small) — ✅ shipped
- `lib/content-blocks.ts` with types + constants + `textToTipTapHtml` + `resolveContentBlocksForQuote`
- Firestore security rules update — uses `isSignedIn()` for `contentBlocks/*` matching every other org subcollection. Org-admin enforcement is at the UI layer via `organisation.permissions[role].can_access_settings` (the same gate the parent `/manage` page uses). Rule-layer org-admin checks have false-positive risks per the v1.6.1 sub-dealer lesson.
- Unit test for `textToTipTapHtml`: SKIPPED — repo has no unit-test framework (only Playwright E2E). Helper is small + obvious + exercised empirically by the auto-migration in Phase B; a Playwright migration smoke test in Phase B+ covers it. Adding vitest just for this would violate "don't introduce abstractions beyond what the task requires".

### Phase B — Tab shell + master-detail layout + auto-migrate
- New "Quote Content" tab in `manage-organisation-page.tsx`
- `quote-content-manager.tsx` master-detail layout
- `content-block-list.tsx` with the 7 fixed block types (lists ALL types whether they exist as docs or not — clicking an unsaved type creates a doc lazily on first save)
- Auto-migrate effect on first open if `organisation.termsAndConditions` has content + `contentBlocks` is empty
- "Selected" state defaults to terms-and-conditions

### Phase C — Editor + version history
- `content-block-editor.tsx` wires the TipTap editor to the selected block
- Save on blur + explicit "Save" button
- Every save appends a version doc to `contentBlocks/{blockId}/versions/`
- `version-history-drawer.tsx` reads versions ordered by savedAt desc, click row to preview, button to restore (creates a new version with the restored content as the latest)
- Cap at 20 versions per block; older ones auto-pruned (`onSnapshot` listener triggers pruning)

### Phase D — Brand overrides
- `brand-override-picker.tsx` shows: "Org default" + dropdown of every distinct `vendorId` from `modules/{moduleId}` docs the org has access to
- Switching the picker loads the override doc (or shows "No override yet — using default" with a "Customize for this brand" button)
- Editing in brand-override mode writes to `contentBlocks/{blockId}/brandOverrides/{vendorId}` (not the parent)
- Version history still appends per save, with `level: 'brand:{vendorId}'`

## 7. UX details worth pre-deciding

### Empty-state for unsaved block types
The list shows all 7 blocks. Most won't have docs in Firestore initially (empty org). Click "Salesperson Message" → editor opens with empty TipTap → user types → on first save, a doc is created with a client-side ID via `doc(collection(...)).id` (matches v1.5 pattern, with the v1.5.1 lesson applied — regenerate per editor open if the editor is mounted at the page level).

### Save semantics
- TipTap onUpdate writes to local draft state (not Firestore — per v1.5 lesson "TipTap onUpdate fires per keystroke").
- Save triggers: (1) editor blur, (2) explicit Save button, (3) brand-override-picker switch (warn if dirty).
- Each save appends a version doc — including the auto-migrated initial save.

### Brand-override visual cue
List items show:
- 🔘 (no doc yet) — block type defined but no content
- ✏️ (has default content) — block doc exists, no overrides
- 🎨 (has overrides) — block doc + N brandOverride subdocs

### History drawer
Versions show: `savedByName · 2 hours ago · "Default" or "Brand: Highfield"`. Hover preview, click to expand into a side-by-side diff with current.

## 9. Open questions (for sign-off before Phase A)

### Q1: Where do block-type DEFAULTS live (the seed text)?
The seed acceptance for 1.2.1 implies there's a "Why Northside Marine" / "Life Beyond the Shore" copy that needs to come from somewhere. Three options:
- **(a)** Hardcode defaults in `lib/content-blocks.ts` as fallback (simple, but every org sees the same default — 1.8.1's whole point is per-org customization).
- **(b)** Ship empty defaults in 1.8.1; org admin authors all 7 blocks themselves before they get a meaningful PDF.
- **(c)** Ship empty defaults BUT a "Suggest content" button per block that pre-fills with a generic template the admin can edit.

Recommend **(b)** — keeps 1.8.1 scope clean, and orgs that don't author content just get the existing "no extra blocks" PDF (which 1.2.1 still produces a valid quote for, just less branded).

### Q2: What's the brand-override picker's source of brand options?
Two options:
- **(a)** Distinct `mainVendorId` across the org's enabled modules (queries `modules/{moduleId}` docs).
- **(b)** Distinct `vendorId` across the org's existing quotes (queries `users/{userId}/quotes/*`).

Recommend **(a)** — modules are the authoritative source of "which brands does this org sell". Quotes are downstream.

### Q3: Does the brand-override surface need to handle motor-only / trailer-only quotes?
Some quotes don't have a single dominant brand (mixed motor + trailer + dealer-fit). The vendorId field on the quote may be the boat vendor, OR null for non-catalog modules.

Recommend: when `quote.vendorId` is null, the PDF uses org default for every block. No multi-brand merging in 1.8.1 — that's a v1.8+ enhancement if it becomes a real need.

### Q4: Security rules for the new subcollections
The existing org subcollections allow read+write for org members. Should `contentBlocks` be tighter — e.g. only org admins can write, all members can read?

Recommend: **org admins only** for write (since this affects every customer-facing PDF). Reads can be open to all org members.

### Q5: Should we ship the v1.8.3 `startsOnNewPage` schema field now?
Pro: avoids a future Firestore migration when 1.8.3 lands.
Con: schema-only field with no UI is ugly.

Recommend: ship the schema field NOW (default false), don't expose UI. 1.8.3 just adds the toggle.

## 10. Risks + mitigations

| Risk | Mitigation |
|---|---|
| Auto-migration runs on every tab open if logic is wrong → duplicate T&Cs blocks | Strict guard: `contentBlocks.length === 0 && organisation.termsAndConditions`. Idempotent because the second condition becomes vacuous after migration. Add a unit test for the guard. |
| TipTap editor mounted at tab level may bleed drafts across blocks | Apply v1.5 lesson — wrap editor body in a sub-component keyed by `block.id` so drafts reset on switch. |
| Version count grows unbounded if pruning is buggy | Cap at 20, log when pruning fires, add an integration test that creates 25 versions and asserts the count drops to 20 after the next save. |
| Brand-override edits silently overwrite each other if two admins edit simultaneously | Acceptable for v1.7 (small team, low concurrency). v1.8+ could add presence indicator. |
| PDF render relies on 7 blocks but org has authored 0 | Fallback chain in 1.2.1 (block → legacy T&Cs field → DEFAULT_TERMS hardcoded). Other 6 block types just don't render their section. |
| Existing `organisation.termsAndConditions` textarea still visible in Document Templates tab — confusing | Hide it once the org has any content blocks. Show a banner: "T&Cs is now managed in the Quote Content tab." Tiny UX add to Phase B. |
